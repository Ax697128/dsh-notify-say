**背景**：外部审查（2026-10-19）基于 v0.4.64 源码，发现 4 个「错误没有声音」的缺陷。
**严重度高于空闲门** —— 完成提醒晚一点只影响体验，错误没提醒可能让人离开很久才发现。

| 2.2 | **后台 job failed 无独立播报路径** | 全文件搜不到 `'failed'`/`'killed'`；`jobs.events` 回调只调 `reevaluatePending` | **P0** | ✅ 已修（handleJobFailure）|
| 2.3 | **缺 reason 默认 completed + 复用旧 reason** | `rec && rec.kind ? rec.kind : 'completed'`；`lastTurnEnd` 只在卸载时 clear | **P0** | ✅ 已修（带轮次+消费即删）|

**修法要点**：
- 去抖分级：`fail` 不被 `completed` 压制，反之亦然（按 kind 分桶记时间）
- 相同错误事件用稳定 ID 去重，防重复播报
- 后台 job failed → 独立失败播报（关联 job id 去重）
- 主回合与子任务报同一失败 → 合并为一次
- 缺 reason → 引入「原因未知」状态，**不默认 completed**
- `lastTurnEnd` 按轮次消费（处理完删除）
- spawn 记录：启动成功 / 失败 / 退出码非零，失败时有限次降级到系统蜂鸣

### 第 3 批：error 当场播报 + 语义细化（进行中）

**核心改动（2026-10-19 从真实数据查出的根因）**

原链路：`turn/end(error)` 只记账 → 等 `agent/status` 转 idle → 才播报。
**多了"等 idle"这个脆弱依赖**：那个边沿若没来/晚来/被别的状态穿插，错误就永远不播。

用户实测印证：出错时没有语音，是他自己看到界面红色提示、手动发「继续工作」。

**数据支撑**（2195 个真实会话 / 6262 条 turn/end 事件）：
- 同一 turn 出现多条 `turn/end`：**0**（提前播不会重复）
- 同一 turn 出现多种 kind：**0**（不会与 completed 冲突）

**新设计**：
```
error / blocked   → turn/end 当场播，不等 idle（不写 lastTurnEnd）
completed / 其它  → 仍记账等 idle（合并多轮 + 走空闲门）
```

### 第 4 批：Toast 精确跳转会话（2026-10-19 用户提出，已实测可行）

### 需求

现在点 Toast **只能把 DSH 窗口拉到前台**，停在原来的会话上。
用户听到「任务完成」→ 点 Toast → 还得自己去侧栏找是哪个会话完成的。

**目标**：点 Toast → DSH 打开并**直接停在对应会话**。

### 为什么官方路子走不通（已验证）

`app.asar` 里是硬编码的精确匹配：

```js
app.on("open-url", (event, url) => {
  if (url === "dsh://open" || url === "dsh://open/") focusPrimaryWindow();
});
```

`dsh://open?session=xxx` **连窗口都不会拉起**（不是忽略参数，是整个 URL 不匹配）。

### 解决方案：注册自有协议（已实测通过）

```
dshnotify://jump?session=session-abc
     ↓ Windows 调起我们的处理器
RECEIVED: dshnotify-test://jump/?session=session-TEST123   ← 实测收到完整参数
```

2026-10-19 用 `dshnotify-test://` 实测：HKCU 注册 + 启动器脚本收到完整 URL。

**完整链路**：
```
① 播报时   ps1 的 Toast launch = "dshnotify://jump?session=<id>"（需新增 -SessionId 参数）
② 点 Toast Windows 调起协议处理器，收到精确的 session id
③ 处理器   写 bridge 的 pendingJump；再调 dsh://open 复用官方唤窗
④ 前端     window focus 事件 → 读 pendingJump → ui.openSession(id) → 标记已消费
```

### 用户要求：做成**开关式**（2026-10-19 明确）

理由：兼容性更好，不强制所有人接受注册表改动。

### 必须做完整的闭环（用户 2026-10-19 明确强调）

| # | 环节 | 要点 |
|---|---|---|
| 4.1 | **配置开关** | `toastJumpSession`，**默认 false**；GUI 加一个 toggle（复用现有设置页风格，不新增布局）|
| 4.2 | **协议注册** | 插件启动时写 `HKCU\Software\Classes\dshnotify`（无需管理员）；注册前先检测是否已存在且指向正确 |
| 4.3 | **协议注销** | 插件卸载 / 开关关闭时 `Remove-Item` 该键；**不留垃圾** |
| 4.4 | **注册失败降级** | ⚠️ **关键**：注册失败时 Toast 必须回退到 `dsh://open`，否则「点了完全没反应」比现状更糟 |
| 4.5 | **处理器脚本** | 收到 URL → POST 到插件 `/pending-jump` → 调 `dsh://open` 唤窗；脚本自身要健壮（找不到宿主时静默）|
| 4.6 | **前端跳转** | `client.js` 监听 `window.focus`；有 pendingJump 且未消费 → `openSession`；失败 try/catch 静默 |
| 4.7 | **消费与过期** | pendingJump 带时间戳；跳转后标记已消费；超时（建议 120 秒）作废；**队列**而非单值（连续多个完成时按 `multiJumpRule` 取）|
| 4.8 | **旧版 DSH 兼容** | 若宿主版本不支持 `ui.openSession`，功能自动不生效（不报错）|
| 4.9 | **测试** | 注册/注销/重复注册/指向错误/权限不足/处理器异常/过期/队列顺序/会话已删除 |

### 已知取舍（要写进文档）

**无法区分「用户点了 Toast」和「用户自己切回窗口」** —— 但用自有协议后，
处理器只在**真正点击**时才被调起，所以这个问题**解决了**。
剩下的问题是：用户点了 Toast 但 DSH 启动很慢时，焦点事件的时序。

### 风险

- 注册表操作（HKCU 用户级，风险低但需谨慎）
- 处理器脚本的路径依赖（插件目录被移动后失效）→ 注册时写入绝对路径，启动时校验
- 与其它程序的协议冲突（`dshnotify://` 已存在但不是我们的）→ 注册前检测
