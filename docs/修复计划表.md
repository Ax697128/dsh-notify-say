### 第 3 批：error 当场播报 + 语义细化（进行中）

**核心改动（2026-10-19 从真实数据查出的根因）**

原链路：`turn/end(error)` 只记账 → 等 `agent/status` 转 idle → 才播报。
**多了"等 idle"这个脆弱依赖**：那个边沿若没来/晚来/被别的状态穿插，错误就永远不播。

用户实测印证：出错时没有语音，是他自己看到界面红色提示、手动发「继续工作」。

**数据支撑**（2195 个真实会话 / 6262 条 turn/end 事件）：
- 同一 turn 出现多条 `turn/end`：**0**（提前播不会重复）
- 同一 turn 出现多种 kind：**0**（不会与 completed 冲突）

**新设计**：
```
error / blocked   → turn/end 当场播，不等 idle（不写 lastTurnEnd）
completed / 其它  → 仍记账等 idle（合并多轮 + 走空闲门）
```

### 第 4 批：Toast 精确跳转会话（2026-10-19 用户提出，已实测可行）

### 需求

现在点 Toast **只能把 DSH 窗口拉到前台**，停在原来的会话上。
用户听到「任务完成」→ 点 Toast → 还得自己去侧栏找是哪个会话完成的。

**目标**：点 Toast → DSH 打开并**直接停在对应会话**。

### 为什么官方路子走不通（已验证）

`app.asar` 里是硬编码的精确匹配：

```js
app.on("open-url", (event, url) => {
  if (url === "dsh://open" || url === "dsh://open/") focusPrimaryWindow();
});
```

`dsh://open?session=xxx` **连窗口都不会拉起**（不是忽略参数，是整个 URL 不匹配）。

### 解决方案：注册自有协议（已实测通过）

```
dshnotify://jump?session=session-abc
     ↓ Windows 调起我们的处理器
RECEIVED: dshnotify-test://jump/?session=session-TEST123   ← 实测收到完整参数
```

2026-10-19 用 `dshnotify-test://` 实测：HKCU 注册 + 启动器脚本收到完整 URL。

**完整链路**：
```
① 播报时   ps1 的 Toast launch = "dshnotify://jump?session=<id>"（需新增 -SessionId 参数）
② 点 Toast Windows 调起协议处理器，收到精确的 session id
③ 处理器   写 bridge 的 pendingJump；再调 dsh://open 复用官方唤窗
④ 前端     window focus 事件 → 读 pendingJump → ui.openSession(id) → 标记已消费
```

### 用户要求：做成**开关式**（2026-10-19 明确）

理由：兼容性更好，不强制所有人接受注册表改动。

## 🚧 明天继续：第 4 批精准跳转的遗留问题（2026-10-19 23:59 记录）

### 状态

### 两个已定位的问题

#### ① `jumpProtoState` 在热重载后丢失（我的设计错误）

**证据**：日志里 `[jump-proto] state=off` 被写入**上百次**（22:54–23:26），
说明 `apply()` 被反复调用（每次热重载都跑一遍）。

**根因**：
- `jumpProtoState` 和 `cfg` 都是**模块级变量**，热重载后重置
- `cfg` 重置成默认值 → `toastJumpSession: false` → 判成 `off`
- 即使加了 `refreshConfig()`，23:24:37 注册成功后，**后续某次重载又把它覆盖回 off**

**修法建议**：
- 不要依赖内存状态，改成**从注册表实际探测**：
  ```js
  function probeJumpProtocol() {
    // 读 HKCU\Software\Classes\dshnotify\shell\open\command
    // 若存在且指向我们的 jump-handler.ps1 → 'ok'
  }
  ```
- `syncJumpProtocol` 先 probe 再决定是否注册（幂等，且不受重载影响）
- 或者把状态写到 bridge 侧（跨重载存活）

#### ② `jumpWhenForeground: false` 导致前台不跳

**用户当前配置**：
```
jumpWhenBackground: true
jumpWhenForeground: false   ← 前台完成不跳
```

`jumpEnabled()` 返回 `jumpWhenForeground: false`，`shouldJump` 会拒绝前台跳转。

**需要用户决定**：是否把 `jumpWhenForeground` 也打开？
（用户 2026-10-19 明确想要「前台点 Toast 也能无脑跳过去」→ **应该打开**）

### 为什么用户点 Toast 没反应（完整链路）

```
Toast 的 launch 是 dsh://open（因为 jumpProtoState=off → jumpSid 为空）
  → Windows 调 DSH 本体 → 只 focusPrimaryWindow()，不带 session
```

**日志确认**：完全没有 `[jump-click]` 记录 → 协议处理器没被调起过。

## 📌 经验：涉及前端的改动，先加可观测通道（2026-10-20 用户建议）

### 用户原话

### 为什么这条重要（真实代价）

**因为前端代码完全没有可观测通道：**

## 🛠 开发流程改进：快照回滚（2026-10-20，用户提出）

### 用户的问题

> 「以后你这个代码要不要复制一份？就是说你改动和我这个机子正在运行的那个分离开，这样是不是更规范一点？」

### 结论：**不复制，但加"时间上分离"的机制**

查清事实：

```
运行中的插件 = profiles/desktop/node_modules/dsh-notify-desktop
             = Junction → 开发目录（同一份文件，不是副本）
devReload    = False（改文件不会自动生效）
```

**为什么不该复制**：`dsh-notify-desktop` 在 DSH 里是单实例插件。两份副本会导致
"不知道现在跑的是哪一份" —— 这正是 2026-10-20 排查 8 小时的病灶
（前端代码改了不生效、以为逻辑写错）。

而且今天已有的坑（`$includeFiles` 与 `files` 两处白名单）会变成**三处**
（开发目录 / 运行副本 / 发布包）。

**采用的方案**：保持单目录，用**快照回滚**把风险控制住。

### 新增工具：`tools/snapshot.ps1`

| 命令 | 作用 |
|---|---|
| `.\tools\snapshot.ps1 -Save` | 重载前打快照（自动带时间戳，保留最近 10 份）|
| `.\tools\snapshot.ps1 -List` | 看有哪些快照（含版本号、时间、文件数）|
| `.\tools\snapshot.ps1 -Restore` | 回滚到上一份 |
| `.\tools\snapshot.ps1 -Restore -Name <名字>` | 回滚到指定快照 |

**只备份代码**（`lib/`、`*.ps1`、`*.vbs`、`package.json`、`cordis.patch.yml`），
不备份 `sounds/`（48MB）、`promo/`（116MB）。实测 567 KB / 26 文件，秒级完成。

**关键设计**：`-Restore` 前会先给当前状态存一份 `pre-restore` 快照 —— **回滚本身也可回滚**。

### 为什么这比 `git checkout` 好

今天的真实教训（见坑 #452）：用 `git checkout -- lib/index.js` 回滚改坏的代码，
把**同文件里其它已改好的**东西一起冲掉了（`/log` 端点消失，前端日志全丢）。

- `git checkout` = 回到 HEAD（整文件、丢掉所有未提交改动）
- 快照回滚   = 回到"我 5 分钟前的样子"（只丢这 5 分钟的）

故意把 `lib/protocol-ownership.js` 改成 35 字节垃圾 → `-Restore` →
恢复成 4398 字节、内容完好、`node --check` 通过。全量测试 522+26 全绿。
